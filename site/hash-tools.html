Hash Tools.

Three one-way functions, three widths — 128, 160 and 256 bits. Type anything and watch it collapse into a fixed-length hex fingerprint on every keystroke: flip one bit of the input and roughly half the digest flips with it. The input is read as UTF-8 bytes, so Persian and emoji hash correctly, and the classic fox test vector is one click away for verification. Deterministic, irreversible, and computed entirely in your tab — nothing is uploaded, nothing is stored.

MD5 Generator

runs in the bench above

The 1991 workhorse that still refuses to retire. MD5 folds any input into a 128-bit digest — 32 hex characters — in 512-bit blocks, and it does it fast. It has been collision-broken since 2004 and is trivially forgeable today, so it has no place near passwords, signatures or certificates. But as a quick, non-adversarial fingerprint — checksums, cache keys, dedup, change detection — it remains exactly what it always was: cheap and good enough. The bench shows the digest byte-by-byte, with the block count and compute time alongside.

SHA1 Generator

runs in the bench above

NSA's 1995 design produces a 160-bit digest — 40 hex characters — and for two decades it signed the web's certificates. Then SHAttered (2017) produced a real collision, and it was retired from security duty. Today it lives on in legacy corners — old version-control fingerprints, protocol compatibility, non-adversarial content IDs — where its width and speed still earn their keep. Anything security-sensitive should move to SHA-256, which is one tab away.

SHA256 Generator

runs in the bench above

The current standard. SHA-256 compresses any input into a 256-bit digest — 64 hex characters — and has no practical attacks after two decades of scrutiny. It underpins TLS handshakes, code-signing, blockchain, file integrity and the salted password pipelines that wrap it. If one of these three algorithms is going anywhere near something an attacker might care about, this is the one. The avalanche is on full display: change the last character of the input and the whole digest reshuffles.

Questions

Asked often, answered plainly.

( 02 )
Can you reverse a hash back to the original text?

No — cryptographic hashes are one-way by design. There's no decryption; the only way back is guessing, via brute force or dictionary attacks against short, predictable inputs. That's exactly why passwords should never be stored as raw MD5 or SHA — they need slow, salted password-hashing functions like bcrypt or Argon2, which make each guess expensive.

Why does my text hash to more bytes than it has characters?

Because the algorithms hash bytes, not characters, and this bench encodes your text as UTF-8 first. ASCII characters are one byte each, but Persian letters are two bytes and emoji are four — so the Input bytes readout can be well above the character count. The same text always produces the same bytes, and therefore the same digest, on every machine.

Which algorithm should I use?

SHA-256 for anything an attacker might care about — signatures, integrity checks, tamper detection, anything security-related. MD5 and SHA-1 both have practical collision attacks and are deprecated for security; keep them only for checksums, cache keys, deduplication and legacy compatibility where nobody is deliberately crafting malicious input.

Are MD5 and SHA-1 still useful for anything?

Yes — just not for security. A broken hash still works perfectly as a fast fingerprint when there's no adversary: file checksums, cache keys, content deduplication, change detection, database sharding. The collision attacks only matter when someone can deliberately craft two different inputs that produce the same digest, and that takes real resources.

Is my data saved anywhere?

No. IrisTool has no backend and no database. Hashing happens inside your browser tab and the input disappears the moment you close or refresh the page. There is nothing to leak, because nothing is ever collected — and even a hash of it never leaves your machine.
